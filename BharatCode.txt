ScopeBot — BharatCode Build League Harness Documentation
================================================================================

1. MODEL OVERVIEW & OPTIMIZATIONS
--------------------------------------------------------------------------------
- Model Identifier: qwen-3.8-27b
- Upstream Base URL: https://bharatcode.ai/api/model/v1
- Protocol: OpenAI-Compatible Chat Completions API (/chat/completions)
- High-Performance Optimizations:
  * Streamed Generation: Calls chat completions with `stream: true` to prevent
    idle socket closures and read Server-Sent Events (SSE) deltas directly.
  * Server-Side Assembly: Assembles the raw JSON stream in real time.
  * Max Tokens: Set to 2,500 tokens per call (drastically lowering inference
    latency compared to large 4k+ runs).
  * Compact JSON: Prompts enforce concise strings, a maximum of 8 tasks, and
    a maximum of 5 milestones to keep generation ultra-fast.
- Server Route Timeout & Keepalive:
  * `export const maxDuration = 300` configured on the Next.js server route.
  * Upstream call timeout set to 240 seconds (4 minutes) with AbortController.
  * Streams SSE keepalive comments (`: keepalive\n\n`) every 10 seconds to
    maintain active connections across proxies while the model is queued.
  * User-facing "Model is queued, this can take a few minutes" status with
    live elapsed timer.
  * Dedicated TIMEOUT error code and user-facing Retry button on failures.
- Credential Security: BHARATCODE_API_KEY is read strictly on the server
  (src/app/api/scope/route.ts). Never bundled into client builds or browser bundles.


2. PARALLEL TWO-CALL HARNESS ARCHITECTURE
--------------------------------------------------------------------------------
To completely eliminate timeouts on heavy briefs, ScopeBot splits the
synthesis workload into two focused parallel calls to `qwen-3.8-27b`:

  ┌─────────────────────────────┐       ┌─────────────────────────────┐
  │           CALL A            │       │           CALL B            │
  │     Solutions Architect     │       │ Technical Delivery & Lead   │
  ├─────────────────────────────┤       ├─────────────────────────────┤
  │ • Scope Summary             │       │ • Task Breakdown (≤ 8 tasks)│
  │ • Core Objectives           │       │ • Hour Estimates & Totals   │
  │ • Key Deliverables          │       │ • Milestone Timeline (≤ 5)  │
  │ • Out-of-Scope Boundaries   │       │ • Professional Proposal     │
  │ • Recommended Tech Stack    │       │   Email Draft               │
  │ • Assumptions & Impact      │       │                             │
  │ • Prioritized Client Qs     │       │                             │
  └──────────────┬──────────────┘       └──────────────┬──────────────┘
                 │                                     │
                 └──────────────────┬──────────────────┘
                                    │
                                    ▼
                         Defensive Merge & Schema
                         Validation (Zod)
                                    │
                                    ▼
                         Final Scope Package

Both calls execute concurrently using `Promise.all()`. This cuts wall-clock
generation time in half (typically ~15–25 seconds total).


3. PROGRESSIVE PER-SECTION STREAMING & KEEPALIVE
--------------------------------------------------------------------------------
When invoked from the web client, the `/api/scope` route supports Server-Sent
Events (SSE) streaming with active keepalive heartbeats:
- Sends `: keepalive\n\n` comments every 10s to keep the client connection
  active without dropping when the upstream model is queued.
- As soon as Call A finishes, the server emits a `partA` event.
  The UI immediately renders Sections 1 (Scope Summary) and 2 (Assumptions &
  Questions) while displaying a lightweight progressive placeholder for the rest.
- As soon as Call B finishes, the server emits a `partB` event.
- The server validates and merges both parts, emitting a `complete` event.
- If a client requests standard non-streaming JSON (e.g. curl or external test),
  the route cleanly falls back to standard HTTP 200 JSON.


4. INSTANT SAMPLE OUTPUT FOR JUDGES
--------------------------------------------------------------------------------
To ensure hackathon judges can immediately inspect the complete 5-section UI,
hour breakdown tables, timelines, and proposal drafts without waiting on a
busy model queue:
- A dedicated "Sample output" view of the KiranaFlash scope is accessible with
  one click directly from the header, sidebar, loading state, and empty screen.
- Clearly marked with a prominent `Sample output` badge.


5. DEFENSIVE VALIDATION & RETRY ON BAD JSON
--------------------------------------------------------------------------------
Both Call A and Call B feature independent self-correction loops:
- Step 1: Strip any `<think>...</think>` traces from Qwen reasoning.
- Step 2: Extract JSON from code blocks or outermost matching braces.
- Step 3: Validate against `ScopePartASchema` or `ScopePartBSchema`.
- Step 4: If Attempt 1 produces malformed JSON or fails schema constraints:
  The harness extracts the exact Zod error paths and issues a focused retry
  prompt (`buildPartARetryPrompt` / `buildPartBRetryPrompt`), allowing the model
  to fix the violation on Attempt 2.
